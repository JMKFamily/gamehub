## 요청 받은 일
오케스트레이터가 요청자 지시(2026-11-17, 전 프로젝트) "판정 이름과 퍼센트까지 해주세요."를 전달했습니다. 탭마다 판정 이름과 DJMAX식 정확도 %를 보여 주고, 결과 화면에 레벨 정확도 %와 최고 콤보를 보여 줍니다. 클리어·실패·난이도(30회 한도)와 물리·판정 창·`judge_taps`는 바꾸지 않습니다. 중간에 사용 한도로 멈췄다가(22:51 재개) 같은 범위로 이어서 끝냈습니다.

## 한 일
1. `balance.json combo.judge_pct`를 추가했습니다.
   - 계단: 100 / 90(딱), 80 / 70 / 60(좋아), 50~10(통과, 이른 쪽·늦은 쪽 창 끝 따로 5칸).
   - Δ는 틱 기준이고 0.001 ms로 반올림합니다. 창 끝 허용 오차는 0.15 ms입니다.
   - 정확도 = 클리어한 시도의 판정 % 평균을 내림한 값입니다. 실패 시도·연습 모드는 null입니다. 기록은 일반 모드 최고값입니다.
   - 표시 시간: 80 / 400 / 150 ms, 새 판정이 오면 바꿔 그립니다.
2. `tools/sim/combo-ref.mjs`
   - `deltaMs`·`pctOf`·`gradeFromPct`·`accuracyOf`·`updateBest`를 넣었습니다.
   - 판정 결과에 `pct`를 더하고, 훅 `lastPct`·`accuracy`, `onClear()`, `{pct:false}` 끄기 옵션, 디버그용 `unmatched`를 넣었습니다.
3. **버그 수정**: `combo-ref.mjs`가 판정 창을 없는 키(`judge_early_ms`/`judge_late_ms`)로 읽고 있었습니다. 창이 NaN이 되어, 모든 점프가 창과 상관없이 탭과 짝지어졌습니다. 이를 `early_ms`/`late_ms`로 고쳤습니다. 빌드에는 아직 콤보 구현이 없어 영향은 없습니다.
4. `tools/combo-check.mjs`에 P1~P5를 추가했습니다.
   - P1: 창 안 모든 틱에서 % → 등급이 판정 등급과 일치
   - P2: 창 끝 = 10 %
   - P3: 봇 판정마다 % → 등급 일치
   - P4: % 층 켠/끈 결과 불일치 0
   - P5: 정확도 계산
   - 정확도·% 분포 출력도 넣었습니다. B1(클리어 런 판정 수 = 탭 수)은 버그 수정 뒤 실제 불일치가 드러나 **경고**로 바꿨습니다(아래 문제 1).
5. Δ를 0.001 ms로 반올림하도록 했습니다(`deltaMs`). 정확히 ±25·±50·±100 ms에 떨어지는 틱(박이 틱 위에 놓이는 레벨 1·2·4·8)이 부동소수 오차로 바깥 등급으로 가던 것을 "경계는 이하" 규칙대로 고쳤습니다. 경계 값은 그대로이고, 1단 비율이 약 1~2 %p 오릅니다. 생사 영향은 0입니다.
6. `20-balance.md` 15-10절을 썼습니다: 계산, 검사, 정확도·% 분포, 바뀌지 않는 것, 찾은 문제, dev·qa·art 인계. 머리말과 13장 이력에도 한 줄씩 넣었습니다.
7. `10-lore.md`
   - 5-9절(판정 이름 3개, `judge_pct`, 결과 화면 라벨·대체 글 9키)을 넣었습니다.
   - 확정값 표에 판정 이름 줄을 넣었습니다.
   - 5-8절의 `aria-valuetext` "퍼센트로 읽히지 않게" 설명을 콤보 점 줄·콤보 표지에만 해당하도록 고쳤습니다.
   - 처리 결과 절을 덧붙였습니다.

## 문제·남은 일
1. (major, 오케스트레이터 결정 → balance) **짝 없이 살아남는 탭**
   - `safe_*`는 "그 탭 하나만 옮겼을 때" 살아남는 범위입니다. 앞 탭이 어긋나면 박 기준 창 밖에서 뛰어도 살아남는 경우가 있습니다(σ70 클리어 런의 약 0.6 %, 주로 고리 탭).
   - 콤보는 끊기지 않고 그 탭만 이름·%가 안 뜹니다. 15-8의 "판정 수 불일치 0"은 버그 탓에 나온 값이었습니다.
   - 판정 창을 바꾸지 말라는 범위라 그대로 두었습니다. 후보: `judge_pad_ms` 상향, 또는 고리 탭은 닿은 구간 기준 창(20-balance 15-10-6).
2. (major, game-developer) `judge_pct` 계산·표시·결과 화면·`bestAccuracy`를 구현해야 합니다. 훅은 `lastPct`·`accuracy`·`bestAccuracy`, `grades[].pct`입니다. Δ 0.001 ms 반올림과 창 끝 0.15 ms 허용 오차를 combo-ref와 똑같이 해야 합니다.
3. (major, art-director) 판정 이름 + % 두 줄 글꼴·크기·자리, 결과 화면 그림표가 필요합니다. 30-art의 "판정 글자 팝업 금지" 줄도 고쳐야 합니다.
4. (minor, qa-engineer) 빌드 훅과 combo-check를 같은 입력으로 비교해 주세요. 클리어 런 판정 수 검사는 "= judge_taps 길이"가 아니라 "combo-ref와 같음"으로 봐야 합니다.
5. (minor) 15-4·15-8 등급 분포 표는 버그 영향이 있던 값이라 기록으로 남겼습니다. 새 값은 15-10-4입니다.

## 다른 팀에 줄 인사이트
- 기준 구현(ref)과 검사기가 같은 잘못된 키를 읽으면 NaN 비교가 "항상 통과"가 되어 검사가 아무것도 못 잡습니다. 데이터 키를 읽는 곳에는 값이 숫자인지 확인하는 단언을 넣거나, 일부러 틀린 입력을 넣었을 때 FAIL이 나는지 확인하세요. 근거: runner-01 20-balance.md 15-10-6. 적용: balance·qa는 판정 검사 도구에 "일부러 틀린 입력 → FAIL" 자가 검사를 하나씩 넣습니다.
- 틱으로 판정하는 게임에서 % 계단 경계는 부동소수 오차로 갈릴 수 있습니다(정확히 100.000 ms). Δ를 작은 단위(0.001 ms)로 반올림한 뒤 비교하고, 반올림해 저장한 창 값(0.1 ms)에는 허용 오차를 두세요. 근거: 같은 절 15-10-1. 적용: rhythm 팀 balance·dev도 같은 방식을 씁니다.
- "그 노트 하나만 옮겼을 때 살아남는 창"을 판정 창으로 쓰면, 앞 입력이 어긋났을 때 살아남는 점프가 창 밖에 날 수 있습니다(러너형). 판정 창을 만들 때는 앞뒤 입력을 함께 흔든 봇 표본으로 "생존 = 판정" 비율을 재세요. 근거: 15-10-6.
